# AI model and effort selection

Read this before testing here. While prompts change quickly no ladder runs on a prompt change (see "Development phase" under Policy); when one does run, check the Test coverage index first so you do not repeat a test. It records which model and effort each AI call uses, the policy that decides them, how to measure a setting, and what is known (little) about every call. A call marked **Proven** needs no re-test until one of the re-test triggers applies; anything else is an untested default.

Where the settings live: `TASK_PROFILES` in `scripts/claude-gateway.mjs`, one entry per operation. Every operation runs its profile's model and effort at every stage; no per-stage override exists. Every call is one signed-in Claude CLI call made through the local relay (`scripts/bridge-server.mjs`, `POST /api/bridge`). The profile also holds a timeout and the payload keys that go into the cached system prompt. The operations are in [AI tasks](AI_TASKS.md).

No measurement data survive for the choices made before 2026-11-11. Until 2026-11-10 the gateway recorded no usage, cost or resolved model; it now does (see How to measure). Every setting below rests on the 2026-11-11 and 2026-11-12 ladders in Measured results.

## Policy

### Development phase (from 2026-11-14)

Prompts change quickly, so a ladder result can go stale within a day of being measured. Until the prompts are frozen (the user's decision, 2026-11-14):

- **No ladders on a prompt change.** The re-test triggers below still decide which results are stale, but a stale call is noted and left alone. Do not run ladder arms or the judge to re-prove a setting unless the user asks.
- **Settings come from reasoning.** An existing call keeps its current `TASK_PROFILES` setting: the last measured knee is the best prior available. A new or heavily rewritten call gets a setting chosen by judgement from the nearest measured call of the same kind, erring one step up in quality, so that a bad reply points at the prompt and not at the model.
- **Validity smoke check after a contract change.** When a call's prompt, payload, schema or validator changes, replay a handful of cases at the current setting only and read the valid rate: `npm run ai:ladder -- run --cases <file> --settings <current model:effort> --name <name>`, with no other arm and no judge. This costs cents and is what caught the broken contracts on 2026-11-11 and 2026-11-12 (a missing validator case, replies 0-54% valid on the first try). It proves the contract works, not that the setting is the knee.
- **One optimisation pass at the end.** Once prompts are frozen, run the full knee method below on every call in one pass, on real captured payloads where the store holds enough. That pass also closes the synthetic-cases gap.

The hard exclusions below apply in every phase.

### Hard exclusions

- Never `max` effort. The highest allowed effort is `xhigh`.
- Never Fable. It is not a candidate for any call.
- Always use the latest model through the aliases `haiku`, `sonnet` and `opus`. Never test or pin an older version, even as a control.
- The candidate ladder for every call is Haiku, Sonnet and Opus, each at `low`, `medium`, `high` and `xhigh`: twelve settings, every allowed effort below max.
- The app has only the Claude CLI route, so no other provider is a candidate. (The blind judge uses another model family on purpose; that is measurement, not a production route.)

### Quality knee (every call)

1. Order the candidate settings by **measured cost per call**, never by assumed tier order. Effort mainly changes output cost, so on an input-heavy prompt a lower effort may save nothing and a "cheaper" tier may not be cheaper at all.
2. Start testing at the cheapest measured setting and climb one setting at a time.
3. Stop at the first setting S whose quality no longer improves: the next dearer setting or settings do not beat S by more than the noise floor. Choose S even if it is not the cheapest acceptable setting, and even if a dearer setting is marginally better within noise.
4. Quality must also pass the application's own validator at about the production first-try rate. A setting that needs correction turns pays for them: count retry cost, not just the first reply.
5. Measure the noise floor by running a reference setting twice, or by keeping an unchanged control arm in the same batch. Run order must be shuffled or interleaved so drift does not read as a tier difference.
6. For a stage that feeds another stage (`generate` feeding `tutor` and `assess`), judge the downstream result too, not only the stage's own validator.
7. Generation time is not a criterion. A slower setting that wins on quality is the correct choice.

### Proof

Every call is proven only by a test. Running on the cheapest setting (Haiku at low) proves nothing about quality. Keep each test proportionate to the call's risk: a wrong grade is worth more testing than a question.

### Versions and re-test triggers

Results are tied to model versions, so record the resolved model id with every result (the CLI's init event reports it, and the gateway already checks it against the alias). Re-test a call when:

- a new model version is released in a family it uses (the alias moves under it);
- its prompt, payload schema, JSON schema or validator changes;
- production signals appear: validator rejections, correction turns, retries, or quality drift.

## How to measure

- **Gateway.** `buildPrompt(operation, payload)` and `validateAnswer(job, answer)` are exported, so a runner can replay a captured payload through the real system prompt, schema and validator. The gateway accepts `profileFor` (one model and effort per arm) and an opt-in `replaySamples` store.
- **Tutor prompt cache (2026-11-19).** The CLI caches the system prompt whole and nothing inside the message, which opens with the request id. A tutor profile therefore lists every key that is byte-identical across the turns of one question in `stableKeys` (curriculum, roadmap progress and topic context included), and `changing` names the parts of those keys a turn can alter (probe facets, topic observations, the knowledge notes at the end of `progressContext`), which stay in the message. `tests/tutor-prompt-cache.test.ts` guards this with the app's own payloads. Before this, each turn rewrote about 130,000 tokens (about $0.54) and only an identical resend hit the cache. The new layout moved reference material from the message to the system prompt, so the tutor setting is due a re-test; its live cost effect has not been measured.
- **Per-call usage log.** The relay writes one row per CLI invocation, correction turns included, to `.local/bridge-service/claude-usage.jsonl` (owner-only, rotated to `.1` above 5 MB). A row holds the operation, `attempt` (0 first try, 1 correction), alias, effort, resolved model id, `costUsd`, input/output/cache tokens, CLI turns, wall and API duration, `firstTextMs` for streamed calls, and `outcome` (`accepted`, `rejected`, `schema-rejected`, `timeout`, or an error code such as `usage-limit`). An accepted `generate` row also holds `parts` (how many asks the question has, `null` when the reply named none) and `questionChars`; an accepted `tutor` row on a question worked in parts holds `part`, `ofParts` and `partComplete`. Missing numbers are `null`. It never records prompt, reply, validator text, stderr or request ids. `npm run ai:usage` (`scripts/ai-usage-report.mjs`, `--json` for machine output) summarizes it per operation, setting and model: calls, first-try accept rate, corrections, failures, total and mean cost, mean tokens, p50/p95 duration and p95 first-text time.
- **Replay samples.** `ZOMBIE_AI_REPLAY_SAMPLES=1` on the relay keeps the newest real payloads and answers per call, owner-only under `.local/bridge-service/ai-replay-samples/`.
- **Ladder runner.** `npm run ai:ladder` (`scripts/ai-ladder.mjs`) replays case files or the sample store at any `model:effort` list, refuses `max` effort and models other than Haiku, Sonnet and Opus, writes rows to `~/Library/Application Support/zombie-escape-study-game/ai-test-runs/<run>/` as it goes, and resumes.
- **Blind judge.** `npm run ai:judge` (`scripts/ai-judge.mjs`) scores every arm blind (hashed A/B order, the call's own instructions as the rubric) against a reference arm with DeepSeek Flash through `offload complete`, and prints the knee report. The reference arm's repeat run measures the noise floor.
- **Case builders.** `scripts/ai-capture/build-study-cases.ts` builds `generate`, `tutor` and `assess` cases with the app's own payload builders and no network. `build-roadmap-cases.ts` builds `reconcile-roadmap` reject and adopt sets and `score-roadmap-replies.ts` replays each reply through the app's real `reconcileRoadmap`. `build-downstream-cases.ts` builds `tutor` and `assess` cases on the questions a generate arm actually wrote, and `downstream-chains.mjs` joins each question with its tutor reply and assessment into one chain row for whole-chain judging. No builder remains for `review-environment`.
- The cost proxy is the CLI's `total_cost_usd` under a subscription: useful for ordering settings, not an invoice.

Every result row, whatever tool produced it, is copied into this document with the resolved model id and the date.

What it shows:

- All three contracts work at their current settings: every reply passed the validator on the first try.
- `tutor` still leaves out `complete` on a follow-up reply. The combined low and medium run had 5 of 24 such replies (not attributable to a setting); run separately, low had 2 of 12 and medium 3 of 12. That is 10 of 48, about one in five, and no worse at low than at medium, so moving `tutor` up one step would not fix it. The relay reads such a reply as `complete:false`, which is why the valid rate is 100%. The fix, if one is wanted, is in the prompt or in CLI-enforced output, not in the model setting.
- Sonnet low stays the `tutor` setting: medium was no more reliable and costs the same warm.

What it does not show:

- No reply in the 48 tutor runs set `complete:true`, and every case had `helpPolicy.unlocked` empty, so the verdict reply and the hint and given-step paths were not exercised. Ten of the twelve cases are a first turn.
- The runner does not stream, and the malformed JSON seen on real streamed turns did not recur.
- Quality was not judged, so these runs do not re-prove any knee. That waits for the one optimisation pass once prompts are frozen.

## New model release playbook

1. Regression-check the current setting on the new version before changing anything: same sample, same validators, plus planted-defect cases for the judging calls (`assess`, `review-environment`: a correct solution graded wrong, an assisted answer relabelled independent, an observation with no output claimed observed). If it holds, keep it.
2. If the cheaper family improved, step the knee search down one rung and check whether the noise-floor condition now holds there. Step up one rung only if the current setting's quality dropped below the validator or quality floor.
3. Record the new resolved model id and date in the versions table and the results rows.

### `reconcile-roadmap`

Redesign (2026-11-11): the reply no longer carries the whole roadmap. Models refused to write the roughly 430,000-character file back (`canonical` null or empty), so every setting failed. The call now returns `edits`, an ordered list of exact `{find, replace}` edits that the app applies to its own local snapshot (`scripts/lib/roadmap-edits.mjs`; the validator checks they apply), or `outcome: "keep-local"` when the incoming file should not be adopted. Older saved requests that return `canonical` still work. p95 fell from about 20 minutes and $8-10 to about 22-57 s; first calls pay a $1-3 prompt-cache write for the roughly 870,000-character packet.

Sets: a reject set (6 cases where keep-local is right, `scripts/ai-capture/build-roadmap-cases.ts`) and an adopt set (5 cases where adopting is right: 3 administrative revisions recorded per the roadmap's own protocol and 2 built from real study progress), scored by `score-roadmap-replies.ts` as adoptable, rejected or keep-local. Results on the adopt set (adoptable of 10, judge delta rep 0 / rep 1): Opus low 3/10 (-0.6 / 0), Haiku high 4/10 (-2.4 / -2.0), Sonnet high 6/10 (-1.8 / -2.0), Sonnet medium 6/10 (-2.4 / -3.2), Opus medium 5/10 (reference / +0.4), **Opus high 6/10 (+2.4 / +1.8, 100% valid, $1.81 mean, p95 94 s)**, Opus xhigh 6/9 (-1.6 / -0.8, 90% valid, p95 about 18.6 min). Keep-local investigation (2026-11-12): most settings answered keep-local where adoption was correct. Two prompt bugs and the fixture text caused it: the instruction counted the app's own assessed evidence rows as report or AI-authored evidence and read their missing raw work (excluded by design) as missing evidence, and it treated sessions and IDs from the incoming device, not yet in `context.identifierCounters`, as manufactured; the fixtures used placeholder "synthetic" text and fake assessment ids. Remaining issue: on `progress-one-observation`, some replies (Opus high 1, Opus medium 1, Opus low 2) produced edits that are not a direct complete descendant of the local file, so the app rejected them.

## Test plans (hardest prompts per call)

- `generate`: a question that must fit one sitting of at most 15 minutes; an open gap with `reuseInScopeDefinitions: true` where the apex facet must shape the question; several open gaps competing for one bounded question; D1 conceptual diagnosis with an empty starter; a code-review question that must include the helper and its authorization semantics without leaking the verdict. Signal: validator first-try rate (contract copy, stable facets, rubric strings, `estimatedSolveSeconds` 30 to 900), blind pairwise rank on self-containment, visible requirements and no leaked solution, then `tutor` and `assess` on the winning questions. Noise-floor arm: Opus xhigh twice.
- `tutor`: a learner answer that demonstrates a facet by implication (dependents marked `impliedBy`); a declared gap that needs one focused follow-up, not a prerequisite tree; a press for the full answer where a foothold is due; a misconception to correct plainly; a streamed reply whose `text` must appear first. Signal: validator rate on `{text, complete, outcome, knowledge}`, blind review of probe stance, agreement with a reference on `complete` and facet statuses.
- `assess`: planted defects first (a wrong solution marked complete, an assistant-written solution credited as independent, a claim of execution without a runner receipt, a correct but assisted solution, a partially covered scope that must stay partial, a definition issue needing an exact 20-2000 character quote, an assistance source missing from `helpAttributions`), then agreement with a reference on findings, visit outcome and attributions. A validator pass alone proves nothing: these replies are structurally easy and semantically decisive. Use the same cases in interleaved order, current setting twice.
- `review-environment`: a statement with no output (must stay `reported-exposure`), generic code execution offered as hands-on browser or profiling evidence, a real but partial observation, an exact `learnerWorkQuote` present verbatim.
- `reconcile-roadmap`: two snapshots that genuinely conflict, a large uploaded revision where every observation and assessment id must survive, near-identical files (keep-local), and a reply whose edits must produce a direct complete descendant. The most expensive ladder, because each packet is large.

## Web research

No current call uses the internet. `claudeArgs()` passes `--tools ""`, `--setting-sources ""` and `--strict-mcp-config` for every operation, and every prompt tells the model to treat the supplied packet as untrusted data and not to browse links.

Web access would not help `assess`, `review-environment` or `tutor`: they judge supplied evidence, a page cannot verify a learner's artifact, and a model that goes looking for the answer can be steered by it. It would be marginal for `reconcile-roadmap` and possibly useful for `generate` (current library behaviour), at the cost of putting untrusted fetched text into the prompt that designs a graded question. If grounding were ever added, add it to `generate` only, prefer a relay-side search pre-fetch so the CLI keeps no tools, and test it with the same knee method, with verified-source coverage as the quality signal. Recommendation: keep every call offline; no call has a measured quality gap that web access would fill.
