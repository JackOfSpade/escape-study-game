# AI model and effort selection

Read this before testing here. While prompts change quickly no ladder runs on a prompt change (see "Development phase" under Policy); when one does run, check the Test coverage index first so you do not repeat a test. It records which model and effort each AI call uses, the policy that decides them, how to measure a setting, and what is known (little) about every call. A call marked **Proven** needs no re-test until a change to it is triaged as level 2 or 3, or a new model version arrives (see Versions and change triage); anything else is an untested default.

Where the settings live: `TASK_PROFILES` in `scripts/claude-gateway.mjs`, one entry per operation. Every operation runs its profile's model and effort at every stage; no per-stage override exists. Every call is one signed-in Claude CLI call made through the local relay (`scripts/bridge-server.mjs`, `POST /api/bridge`). The profile also holds a timeout and the payload keys that go into the cached system prompt. The operations are in [AI tasks](AI_TASKS.md).

No measurement data survive for the choices made before 2026-11-11. Until 2026-11-10 the gateway recorded no usage, cost or resolved model; it now does (see How to measure). Every setting below rests on the 2026-11-11 and 2026-11-12 ladders in Measured results, and for `lesson` and `lesson-chat` on the 2026-11-20 ladders.

## Policy

### Development phase (from 2026-11-14)

Prompts change quickly, so a ladder result can go stale within a day of being measured. Until the prompts are frozen (the user's decision, 2026-11-14):

- **No ladders on a prompt change.** The change triage below decides each change's level. A level 1 change needs no run, and a level 2 regression check runs as triage describes. A level 3 ladder, or a test of whether a cheaper setting now passes, is noted in the Log and left for the optimisation pass. Do not run ladder arms or the judge to re-prove a setting unless the user asks.
- **Settings come from reasoning.** An existing call keeps its current `TASK_PROFILES` setting: the last measured knee is the best prior available. A new or heavily rewritten call gets a setting chosen by judgement from the nearest measured call of the same kind, erring one step up in quality, so that a bad reply points at the prompt and not at the model.
- **The level 2 regression check replaces the validity smoke check.** Until 2026-11-21 every change to a call's prompt, payload, schema or validator got a smoke check: a handful of cases replayed at the current setting only, reading the valid rate. That caught the broken contracts on 2026-11-11 and 2026-11-12 (a missing validator case, replies 0-54% valid on the first try). Now only a change triaged as level 2 gets a run: `npm run ai:ladder -- run --cases <file> --settings <current model:effort> --name <name>` on the rebuilt cases, with no other arm and no judge, then compared as level 2 describes. A level 1 change gets none. Like the smoke check, it proves the contract still works, not that the setting is the knee.
- **One optimisation pass at the end.** Once prompts are frozen, run the full knee method below on every call in one pass, on real captured payloads where the store holds enough. That pass also closes the synthetic-cases gap.

The hard exclusions below apply in every phase.

### Hard exclusions

- Never `max` effort. The highest allowed effort is `xhigh`.
- Never Fable. It is not a candidate for any call.
- Always use the latest model through the aliases `haiku`, `sonnet` and `opus`. Never test or pin an older version, even as a control.
- The candidate ladder for every call is Haiku, Sonnet and Opus, each at `low`, `medium`, `high` and `xhigh`: twelve settings, every allowed effort below max.
- The app has only the Claude CLI route, so no other provider is a candidate. (The blind judge used another model family, DeepSeek Flash through Offload, on purpose through the 2026-11-12 ladders; that is measurement, not a production route. From 2026-11-20 judging runs with `--judge claude` (Claude Opus high through the CLI; the script's default is still the Offload judge), the user's decision, because the other-family judge runs through Offload, which the owner's rules allow only from an `/offload_*` command. Opus judging arms that include Opus may favour its own family; the blind A/B order removes position bias, not that.)

### Quality knee (every call)

1. Order the candidate settings by **measured cost per call**, never by assumed tier order. Effort mainly changes output cost, so on an input-heavy prompt a lower effort may save nothing and a "cheaper" tier may not be cheaper at all.
2. Start testing at the cheapest measured setting and climb one setting at a time.
3. Stop at the first setting S whose quality no longer improves: the next dearer setting or settings do not beat S by more than the noise floor. Choose S even if it is not the cheapest acceptable setting, and even if a dearer setting is marginally better within noise.
4. Quality must also pass the application's own validator at about the production first-try rate. A setting that needs correction turns pays for them: count retry cost, not just the first reply.
5. Measure the noise floor by running a reference setting twice, or by keeping an unchanged control arm in the same batch. Run order must be shuffled or interleaved so drift does not read as a tier difference.
6. For a stage that feeds another stage (`generate` feeding `tutor` and `assess`), judge the downstream result too, not only the stage's own validator.
7. Generation time is not a criterion. A slower setting that wins on quality is the correct choice.

### Proof

Every call is proven only by a test. Running on the cheapest setting (Haiku at low) proves nothing about quality. Keep each test proportionate to the call's risk: a wrong grade is worth more testing than a question.

### Versions and change triage

Results are tied to model versions, so record the resolved model id with every result (the CLI's init event reports it, and the gateway already checks it against the alias). A new model version released in a family a call uses (the alias moves under it) follows the New model release playbook. Every other change to a call is triaged as below (adopted 2026-11-21; before then any change to a call's prompt, payload schema, JSON schema or validator was a re-test trigger).

**Baseline per call.** Every row in Current settings records its baseline: the commit of the call's prompt-building code (prompt, schema, validator, tools) when it was last tested, and which recorded prompts that test used. A level 2 pass or a recorded level 3 choice moves it; nothing else does. For a row whose test predates this rule, the baseline is the commit current on the row's test date (`git log -1 --before=<date> -- <call files>`). Where that run used fixes not yet committed, it is the commit that records them, and the row says so. If it cannot be determined, write "unknown" and treat the call's next change as level 2.

**Call files.** The files whose difference decides the level:

- every call: `scripts/claude-gateway.mjs` (system prompt, preamble, CLI tools) and `scripts/lib/` (instructions, output rules, validators, schemas);
- `generate`: also `src/ai.ts` and `src/career-profile.ts`;
- `tutor`: also `src/ai.ts`, `src/knowledge-probe.ts` and `src/question-parts.ts`;
- `assess`: also `src/ai.ts`, `src/curriculum.ts` and `src/learning-assessment.ts`;
- `review-environment`: also `src/ai.ts` and `src/environment-review.ts`;
- `reconcile-roadmap`: also `src/roadmap-adoption.ts`;
- `lesson` and `lesson-chat`: also `src/lesson.ts`.

**Compare with the baseline, never with the previous revision.** When a call changes, assess the whole difference since its baseline: `git diff <baseline>..HEAD -- <call files>`. Compare the instructions and output rules, not the per-call data a payload carries. Small changes add up: after original, rev1 and rev2, rev2 is assessed against the original.

**Pick a level** from that difference and record it in the Log with a one-line reason:

1. **Level 1, no test.** The change cannot plausibly move the choice: wording, examples, reordering, a rule the host enforces in code, more of the same input, host bug fixes, renames. The baseline does not move.
2. **Level 2, regression check.** The task got somewhat harder: a new strict output rule (exact copy, ids or quotes), a stricter validator, noticeably longer input. Run only the current setting, once, on the baseline's prompts rebuilt with the current code, through the app's own validator, and compare with the baseline's stored answers. Pass: the baseline moves to the current commit. Fail: go to level 3.
   - **Rebuild, never replay as stored.** A stored payload carries the instructions it was built with, so replaying it unchanged re-tests the baseline, not the change. For built cases, rerun at HEAD the builder that made the baseline's case file (Case builders under How to measure): apart from random ids and wall-clock times it builds the same cases, now with the current instructions (checked 2026-11-21 for `build-study-cases.ts`, `build-roadmap-cases.ts` and `build-lesson-cases.ts`). A stored production payload from the replay store cannot be rebuilt, so replace the fields that carry instructions with what the current code produces: `generationPolicy` and `careerScopeGuidance` (`generate`), `instruction` and `responseFormat` (`tutor`, `lesson-chat`), `packet.assessmentPolicy` (`assess`), `instruction` (`review-environment`, `reconcile-roadmap`) and `lessonPolicy` (`lesson`). No script does this yet. The gateway builds the rest of the system prompt from the current code on every run, so only the payload goes stale.
   - **Compare** with the answers the baseline run stored (`results.jsonl` in its run folder), and with stored production answers where the replay store holds them for the same prompts. Pass means valid on the first try at about the baseline run's rate, and no answer worse than its baseline answer, read side by side, on what the change asked for.
3. **Level 3, full ladder.** The change could plausibly move the choice either way: a new task, judgement or output type; a new kind of input (images, a new evidence source); tools added or removed; the call moving between live and not live; a changed latency budget. Ladder the call as Quality knee describes. The baseline moves when the new choice is recorded.

When unsure, use level 2.

**Direction matters.** A change that makes the task easier warrants only a test of whether a cheaper setting now passes, and only for a call that is expensive or runs often. A change that makes it harder starts with a level 2 regression check.

**Unchanged rules.** A call that has never been tested still needs its first test; a setting chosen by analogy stays a placeholder. A new model release follows the New model release playbook. A production signal (rising validator rejections, correction turns or retries, or quality drift) goes straight to level 2, whatever the difference says.

## How to measure

- **Gateway.** `buildPrompt(operation, payload)` and `validateAnswer(job, answer)` are exported, so a runner can replay a captured payload through the real system prompt, schema and validator. The gateway accepts `profileFor` (one model and effort per arm) and an opt-in `replaySamples` store.
- **Tutor prompt cache (2026-11-19).** The CLI caches the system prompt whole and nothing inside the message, which opens with the request id. A tutor profile therefore lists every key that is byte-identical across the turns of one question in `stableKeys` (curriculum, roadmap progress and topic context included), and `changing` names the parts of those keys a turn can alter (probe facets, topic observations, the knowledge notes at the end of `progressContext`), which stay in the message. `tests/tutor-prompt-cache.test.ts` guards this with the app's own payloads. Before this, each turn rewrote about 130,000 tokens (about $0.54) and only an identical resend hit the cache. The new layout moved reference material from the message to the system prompt, so the tutor setting is due a re-test; its live cost effect has not been measured.
- **Per-call usage log.** The relay writes one row per CLI invocation, correction turns included, to `.local/bridge-service/claude-usage.jsonl` (owner-only, rotated to `.1` above 5 MB). A row holds the operation, `attempt` (0 first try, 1 correction), alias, effort, resolved model id, `costUsd`, input/output/cache tokens, CLI turns, wall and API duration, `firstTextMs` for streamed calls, and `outcome` (`accepted`, `rejected`, `schema-rejected`, `timeout`, or an error code such as `usage-limit`). An accepted `generate` row also holds `parts` (how many asks the question has, `null` when the reply named none) and `questionChars`; an accepted `tutor` row holds `mode` (`terminal-dialogue` or `terminal-review`) and `turn` (messages in the conversation so far); a dialogue row adds `complete`, `verdict` (the reply's `solved` or `gap`, kept apart from the row's own `outcome`) when given, and `help` as counts of `nudges`, `hints`, `gives` and `offers`; a review row adds `openGaps` (how many recorded gaps could still close); either adds `facets` as counts of `demonstrated`, `implied` and `gap` when the reply reported any; and a row on a question worked in parts also holds `part`, `ofParts` and `partComplete`. These are counts and enums, never facet ids or text. Missing numbers are `null`. It never records prompt, reply, validator text, stderr or request ids. `npm run ai:usage` (`scripts/ai-usage-report.mjs`, `--json` for machine output) summarizes it per operation, setting and model: calls, first-try accept rate, corrections, failures, total and mean cost, mean tokens, p50/p95 duration and p95 first-text time.
- **Replay samples.** `STUDY_AI_REPLAY_SAMPLES=1` (the old name `ZOMBIE_AI_REPLAY_SAMPLES` is still honoured) on the relay keeps the newest real payloads and answers per call, owner-only under `.local/bridge-service/ai-replay-samples/`.
- **Ladder runner.** `npm run ai:ladder` (`scripts/ai-ladder.mjs`) replays case files or the sample store at any `model:effort` list, refuses `max` effort and models other than Haiku, Sonnet and Opus, writes rows to `~/Library/Application Support/study-app/ai-test-runs/<run>/` as it goes, and resumes.
- **Blind judge.** `npm run ai:judge` (`scripts/ai-judge.mjs`) scores every arm blind (hashed A/B order, the call's own instructions as the rubric) against a reference arm and prints the knee report. The reference arm's repeat run measures the noise floor. `--judge claude [--judge-setting opus:high]` judges through a locked-down Claude CLI call (no tools, settings, MCP or session; run from a neutral folder); without it the judge is DeepSeek Flash through `offload complete`. Every judgment row names its judge, the report warns when a run mixes judges, and a rerun retries pairs that ended in a judge error. Reps are numbered from 0, so pass `--reference <setting> --reference-rep 0`, to `report` as well as to `run`: without it `report` picks its own reference and noise floor.
- **Code-executing blind check (2026-11-20).** The ladder judge reads the answers as JSON (the payload cut at 60,000 characters) and runs nothing. For `lesson` it rated Haiku xhigh level with Opus high, while agents that ran every code block and re-derived every trace frame found it clearly worse. For an output with code or traces, check the knee this way too: write the arms' answers into per-case files under letter labels shuffled per case, keep the key apart, and have one agent per case (or per pair) score them (the 2026-11-20 runs used Claude Code workflow agents on Opus). Measure its own noise floor with the reference setting's repeat run.
- **Case builders.** `scripts/ai-capture/build-study-cases.ts` builds `generate`, `tutor` and `assess` cases with the app's own payload builders and no network. `build-roadmap-cases.ts` builds `reconcile-roadmap` reject and adopt sets and `score-roadmap-replies.ts` replays each reply through the app's real `reconcileRoadmap`. `build-downstream-cases.ts` builds `tutor` and `assess` cases on the questions a generate arm actually wrote, and `downstream-chains.mjs` joins each question with its tutor reply and assessment into one chain row for whole-chain judging. `build-lesson-cases.ts` builds 12 `lesson` cases with `lessonPayload` on gaps recorded by the app's own probe functions, and 12 `lesson-chat` cases captured from the lesson controller's real chat path on three synthetic lessons; `--lessons-from <run dir> --setting <s> [--rep N] --out <dir>` builds the chat cases on lessons a `lesson` arm actually wrote. No builder remains for `review-environment`.
- The cost proxy is the CLI's `total_cost_usd` under a subscription: useful for ordering settings, not an invoice.

Every result row, whatever tool produced it, is copied into this document with the resolved model id and the date.

## Test plans (hardest prompts per call)

- `generate`: a question that must fit one sitting of at most 15 minutes; an open gap with `reuseInScopeDefinitions: true` where the apex facet must shape the question; several open gaps competing for one bounded question; D1 conceptual diagnosis with an empty starter; a code-review question that must include the helper and its authorization semantics without leaking the verdict. Signal: validator first-try rate (contract copy, stable facets, rubric strings, `estimatedSolveSeconds` 30 to 900), blind pairwise rank on self-containment, visible requirements and no leaked solution, then `tutor` and `assess` on the winning questions. Noise-floor arm: Opus xhigh twice.
- `tutor`: a learner answer that demonstrates a facet by implication (dependents marked `impliedBy`); a declared gap that needs one focused follow-up, not a prerequisite tree; a press for the full answer where a foothold is due; a misconception to correct plainly; a streamed reply whose `text` must appear first. Signal: validator rate on `{text, complete, outcome, knowledge}`, blind review of probe stance, agreement with a reference on `complete` and facet statuses.
- `assess`: planted defects first (a wrong solution marked complete, an assistant-written solution credited as independent, a claim of execution without a runner receipt, a correct but assisted solution, a partially covered scope that must stay partial, a definition issue needing an exact 20-2000 character quote, an assistance source missing from `helpAttributions`), then agreement with a reference on findings, visit outcome and attributions. A validator pass alone proves nothing: these replies are structurally easy and semantically decisive. Use the same cases in interleaved order, current setting twice.
- `review-environment`: a statement with no output (must stay `reported-exposure`), generic code execution offered as hands-on browser or profiling evidence, a real but partial observation, an exact `learnerWorkQuote` present verbatim.
- `reconcile-roadmap`: two snapshots that genuinely conflict, a large uploaded revision where every observation and assessment id must survive, near-identical files (keep-local), and a reply whose edits must produce a direct complete descendant. The most expensive ladder, because each packet is large.

## Web research

No current call uses the internet. `claudeArgs()` passes `--tools ""`, `--setting-sources ""` and `--strict-mcp-config` for every operation, and every prompt tells the model to treat the supplied packet as untrusted data and not to browse links.

Web access would not help `assess`, `review-environment` or `tutor`: they judge supplied evidence, a page cannot verify a learner's artifact, and a model that goes looking for the answer can be steered by it. It would be marginal for `reconcile-roadmap` and possibly useful for `generate` (current library behaviour), at the cost of putting untrusted fetched text into the prompt that designs a graded question. If grounding were ever added, add it to `generate` only, prefer a relay-side search pre-fetch so the CLI keeps no tools, and test it with the same knee method, with verified-source coverage as the quality signal. Recommendation: keep every call offline; no call has a measured quality gap that web access would fill.
