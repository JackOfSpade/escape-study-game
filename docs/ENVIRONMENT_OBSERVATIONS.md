# Practical environment observations

The original Product Engineering roadmap defines six environment-backed (ENV) items. Their U/G/P status is separate from chat checkpoints and never blocks a tier gate. A learner's description alone is reported exposure unless relevant output is reviewed, and capturing an observation does not perform or certify that review. An optional model review is described below.

Open Inspect → Practical environment observations (the inspector is opened by coding agents; see the README). Select one of the six source-defined items, describe your own actions, environment, what ran and what you observed (up to 8,000 characters), then optionally attach a finished saved code run or a supporting text, log or shared-code file up to 256 KiB. The full selected scope stays readable below the selector. Saving creates a pending-review observation packet. With the Claude CLI connected and a live learner profile, an explicit **Review observation** action is available. Otherwise use the downloaded packets and the full backup for external review.

A runner attachment includes the immutable captured code and revision, the receipt, image ID and code hash, the actual execution-event sequence and the human-edit references. It must match a runner journal artifact and a reconstructable human-edited source revision. A receipt-shaped object that was merely stored, interrupted jobs, or a different code snapshot cannot be attached. A later editor change does not replace the captured code. This is a fact about execution, not proof that the learner independently wrote tests, implemented a complete feature or met the whole ENV definition.

Learner-supplied files keep their decoded text, filename, text digest and explicit unreviewed provenance. They do not become trusted runner output. Report-only packets contain no claimed runtime observation. Every packet keeps the exact curriculum source and scope, the capture time, the profile it was captured under and its unassessed independence. Full attributed edits and private tutor assistance remain in the complete backup, so a packet alone does not establish independence.

Packets use a separate UUID namespace and allocate no S/A/EV IDs, visits, passes or reviews. Capturing one leaves ENV readiness and the complete merged roadmap unchanged and cannot promote an ENV item, alter an academic checkpoint or satisfy a gate. The authoritative curriculum bytes are preserved.

Packets survive profile changes and JSON backups, and the inspector can download each as JSON. Repeating an identical capture, including concurrent requests or after reload, returns the same packet rather than a duplicate. Each packet carries its own code and receipt or supplied output, so later changes cannot rewrite it.

Persistence failure is explicit: the in-memory packet and its download remain available, the interface does not claim a successful local save, and a retry after storage recovers keeps the same ID. Export the packet or a full backup before leaving if saves fail.

## Explicit practical review

**Review observation** sends the saved packet to the `review-environment` operation. It sends the exact source item and scope, the original capture profile, the statement, and the supplied output or runner receipt. Runner-backed packets also include the original attributed workspace and tutor history through the execution cutoff, including private assistance relevant to the review. Later code or tutor replies cannot replace that captured context. A review happens only on explicit request, with at most one in flight for the learner profile. A packet captured earlier can be reviewed later under a live profile; its original provenance stays unchanged.

The reviewer distinguishes reported exposure (U), partial observation (G) and full source-scope observation (P). G and P need relevant supplied output references, an exact learner-work statement reference and coverage findings. P additionally needs the reviewer's full-scope judgment and no remaining coverage. A generic Python or Node run cannot establish browser rendering, profiling, screen-reader use, repository navigation or end-to-end testing. Text files remain learner-supplied evidence and never become runner receipts. Partial packets do not combine into P or downgrade a prior qualifying observation.

ENV P means observed learner work, not independent academic understanding. Reviews allocate no S/A/EV IDs, visits, checkpoint, transfer or integration passes, retention checks or tier changes. They use separate environment-review UUIDs and append-only practical evidence. The raw packet stays immutable and still reads pending-review; the review queue and the separate evidence record hold the outcome. The merged roadmap carries bounded ENV status, review references and request and judgment digests, not private logs or code.

Outages keep the exact normalized request ID, payload and digest for explicit retry. Reopening the inspector, time passing and reloading never reroll or resubmit it, and a reload marks pending requests interrupted. Replacing the canonical packet, changing the profile or source, missing original runner history, invalid output or ownership references, or an altered saved context prevent a result from being applied. Readiness updates after completion even if the inspector was closed and reopened while waiting. If browser storage fails, the in-memory review and the downloadable evidence backup remain, the failed save is reported, and normal saving and export work again once storage recovers.

Validated reviews project into the six original ENV rows and their separate dashboard count. ENV-only exports preserve protected curriculum bytes, academic ledgers and history, and scheduler queues, update save anchors and migration metadata, and allocate no academic identifiers. Repeated unchanged downloads are byte-identical; further reviews create a new revision with the exact complete prior export as parent. Exports that contain academic attempts also include these practical receipts.

## Verification

`tests/environment-observations.test.ts` and `tests/environment-review.test.ts` cover source, receipt, attribution, idempotency, ownership, retry and export. `tests/browser/practical-observations.spec.ts` exercises the workflow in Chromium, including outage retry, inert rendering of model text and storage failure. Judgments in these tests are synthetic: no learner has been ENV-certified, and the quality of real model reviews is unverified. Browser and React environments, profiling, screen-reader observation, repository and AI-tool workflows still need genuine practical work and review.
